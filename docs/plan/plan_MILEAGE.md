# plan_MILEAGE — правило «пробег не больше 400 000 км»

Дата: 2026-10-07. Задача MILEAGE: если пробег авто больше 400 000 км,
решение по заявке — `review`, а не то, что говорит LTV.

Ревизия 2 (2026-10-07): раздел 3 расширен — полная матрица границ
«399 999 / 400 000 / 400 001 × LTV-зоны», пересечения с границами LTV
(59.99 / 60.0 / 85.0 / 85.01) и границы валидируемого диапазона
(0, -1, 500 000, 500 001).

Ревизия 3 (2026-10-07, по запросу заказчика при реализации): сквозная
e2e-матрица дополнена границами 399 999 и 400 000 в reject-зоне (LTV 95) —
теперь трио границ 399 999 / 400 000 / 400 001 покрыто end-to-end в обеих
зонах решений; закрывает риск инверсии приоритета «reject vs пробег»
на всех границах, а не только на 400 001.

Основа: `docs/setup/code_map.md` (раздел «Правило "пробег > 400 000 км →
review": точки вставки»), разведка @scout из `docs/setup/AGENTS.md`
(все точки чтения `mileage`), проверка кода от 2026-10-07 — строки ниже
совпадают с текущими файлами.

Правило меняет вердикт, а не валидацию: заявка с пробегом 400 001+
остаётся валидной (порог валидации `max_mileage_km` = 500 000), поэтому
правило встраивается в `DecisionEngine`, а не в `ApplicationValidator`
(нарушение в валидаторе = `ValidationException` и отказ обрабатывать
заявку вовсе).

## 2. Шаги

1. **Порог в конфиге.** `rules.php`, блок `vehicle`: добавить
   `'review_max_mileage_km' => 400000` рядом с `max_mileage_km` и
   прокомментировать разницу: `max_mileage_km` — граница валидации
   (свыше — отказ в обработке), `review_max_mileage_km` — порог вердикта.
2. **Красные тесты.** `DecisionEngineTest` — новый провайдер с полной
   матрицей границ (см. раздел 3), движок в setUp конструируется
   с порогом 400 000. `AssessmentServiceTest` — сквозное трио границ
   через фикстуру `payload()`. `ApplicationValidatorTest` — пустой пробег
   и границы диапазона. Прогон `make test`: кейсы «400 001 → review»
   красные; кейсы с пробегом ≤ 400 000 могут быть зелёными уже на старом
   коде — это характеризация, так и задумано.
3. **`DecisionEngine`.** Конструктор принимает `int $reviewMaxMileageKm`;
   `decide(float $ltv, int $mileage): string`.
   - Вариант A (по умолчанию, минимальный diff): `approve` только при
     `LTV < approve_max` **И** `mileage <= review_max_mileage_km`; ветки
     `review`/`reject` по LTV не меняются. При конфликте `reject`
     сохраняется (жёсткий вердикт выигрывает).
   - Вариант B (если ответ на вопрос 1 — «пробег перекрывает всё»):
     первой проверкой `mileage > review_max_mileage_km → REVIEW`, затем
     существующая LTV-логика без правок.
   Док-блок синхронизировать с кодом (сейчас в комментарии `<=`,
   в коде строгое `<` — расхождение отмечено в code_map).
4. **`AssessmentService`.** В `assess()` передать `$input['mileage']`
   вторым аргументом `decide()`. Формат ответа не меняется: при `review`
   `approved_limit` = 0 — уже текущее поведение (строка 39).
5. **`AppFactory`.** Передать `$rules['vehicle']['review_max_mileage_km']`
   вторым аргументом конструктора `DecisionEngine`.
6. **Прогон.** `make test` — всё зелёное; `make lint`. Сверить дифф
   с этим планом: изменённых файлов, кроме перечисленных, быть не должно.
7. **После приёмки** (отдельная задача, не в этом диффе): обновить
   `docs/setup/code_map.md` — раздел точек вставки MILEAGE устареет.

## 3. Тесты

Существующие ассерты не меняем; вызовы `decide()` в старых кейсах
`DecisionEngineTest` получают нейтральный пробег (например, 100 000 км),
чтобы продолжать проверять чистую LTV-логику.

Каждое граничное значение — отдельной строкой; у каждой группы указано,
какой риск она закрывает.

`DecisionEngineTest` — новый провайдер (порог в setUp — 400 000).

Полная матрица «границы пробега × LTV-зоны» — закрывает смещение порога
на ±1 км и протечку пробегового условия в чужие LTV-зоны:

- пробег 399 999, LTV 50.0 (approve-зона) → `approve`
- пробег 400 000, LTV 50.0 → `approve` (граница «не больше 400 000» — включительно)
- пробег 400 001, LTV 50.0 → `review`
- пробег 399 999, LTV 75.0 (review-зона) → `review`
- пробег 400 000, LTV 75.0 → `review`
- пробег 400 001, LTV 75.0 → `review`
- пробег 399 999, LTV 90.0 (reject-зона) → `reject`
- пробег 400 000, LTV 90.0 → `reject`
- пробег 400 001, LTV 90.0 → `reject` (вариант A; при ответе «review» на вопрос 1 — `review`)
- пробег 500 000, LTV 50.0 → `review` (верх валидируемого диапазона)

Пересечения с границами LTV — закрывают инверсию `<=`/`<` в обоих
условиях и смягчение reject-границы пробегом:

- LTV 59.99 (чуть ниже approve_max) + пробег 400 000 → `approve` (обе границы изнутри)
- LTV 60.0 (ровно approve_max, строгое `<`) + пробег 400 000 → `review` (граница LTV сильнее пробега)
- LTV 85.0 (ровно review_max) + пробег 400 001 → `review`
- LTV 85.01 (сразу за review_max) + пробег 400 001 → `reject` (вариант A; при ответе «review» на вопрос 1 — `review`)

`AssessmentServiceTest` — сквозные (фикстура `payload()`, mileage
переопределяем); трио границ end-to-end — закрывает потерю пробега
между валидатором и движком:

- mileage 399 999, LTV 50 → `approve`, `approved_limit = requested_amount`
- mileage 400 000, LTV 50 → `approve`, `approved_limit = requested_amount`
- mileage 400 001, LTV 50 → `review`, `approved_limit = 0`
- mileage 399 999, LTV 95 → `reject`, `approved_limit = 0` (ревизия 3)
- mileage 400 000, LTV 95 → `reject`, `approved_limit = 0` (ревизия 3)
- mileage 400 001, LTV 95 → `reject`, `approved_limit = 0` (вариант A; зависит от вопроса 1)

`ApplicationValidatorTest` — характеризация (код валидатора не
меняется); пустой пробег и границы валидируемого диапазона — фиксируют
область, в которой новое правило достижимо:

- пробег 0 → валиден, нормализуется в 0 (нижняя граница диапазона; сюда же попадает пустая строка)
- пробег -1 → `ValidationException` (сразу за нижней границей)
- пробег 500 000 → валиден (верхняя граница `max_mileage_km`)
- пробег 500 001 → `ValidationException` (новое правило недостижимо, до решения не доходит)
- пустой пробег: ключ `mileage` отсутствует → `ValidationException`, ошибка с ключом `mileage`, решение не выносится
- пустой пробег: `mileage => null` → `ValidationException`
- пустой пробег: `mileage => ''` → нормализуется в 0, валидация проходит, решение по LTV (0 ≤ 400 000, новое правило не срабатывает; см. вопрос 2)

## 4. Риски

1. **Существующая проверка `max_mileage_km` (500 000).** Правило реально
   срабатывает только в диапазоне 400 000 < пробег ≤ 500 000; пробег
   свыше 500 000 — `ValidationException` и отказ обрабатывать заявку,
   а не `review`. Если заказчик ждёт `review` для любого пробега
   > 400 000, придётся менять `max_mileage_km` — отдельное решение
   (вопрос 3), в этот план не входит.
2. **Конфликт решений.** LTV `reject` + пробег > 400 000: вариант A
   сохраняет `reject`, вариант B откатывает в `review`. Выбор меняет
   вердикты в reject-зоне — не финализировать реализацию до ответа
   на вопрос 1. Матрица из раздела 3 фиксирует три вариант-зависимых
   случая (LTV 85.01 и 90 с пробегом 400 001 и сквозной LTV 95):
   при выборе варианта B их ожидания меняются на `review`.
3. **Пустой пробег.** Пустая строка нормализуется в 0 и обходит новое
   правило; отсутствующий ключ / `null` — ошибка валидации. Поведение
   не меняем, но оно неочевидно и требует договорённости (вопрос 2).
4. **Сигнатура `decide()` и конструктора.** Три места конструирования
   (`AppFactory`, два теста) и вызов в `AssessmentService` обновляются
   одним диффом; пропуск обязательного аргумента конструктора —
   `ArgumentCountError` при сборке приложения или setUp теста
   (fail fast, всплывёт на первом же `make test`).
5. **Существующие тесты.** `DecisionEngineTest` вызывал `decide($ltv)` —
   сигнатура меняется. Правка только вызова (нейтральный пробег);
   ассерты и LTV-значения провайдера не трогаем: это адаптация к новому
   API, а не изменение теста ради прохождения.
6. **Док-блок `DecisionEngine`.** Уже расходится с кодом (`<=` vs `<`);
   при добавлении правила комментарий синхронизируется с фактом — правка
   только текста, ветки кода не меняются (ожидаема в диффе).
7. **Конфиг и код одним коммитом.** Забытый ключ
   `review_max_mileage_km` в `rules.php` — warning «undefined array key»
   и `TypeError` (null → int) при сборке контейнера. Оба файла — в одном
   коммите, иначе деплой падает.
8. **`docs/setup/code_map.md` частично устареет** (раздел точек вставки
   MILEAGE). Обновление — отдельная задача документации, в дифф фичи
   не входит.

Не входит: фронтенд (поле `mileage` уже `required`, вердикт `review`
отображается как есть); изменение `max_mileage_km` и текста его ошибки;
контракт API (набор полей ответа не меняется); feature-тесты с БД;
расчёт лимита по `ltv_by_age` (задача LOAN-12); причина `review` в
ответе; миграции БД (`vehicles.mileage_km` не меняется).

## 5. Вопросы без заказчика

1. При конфликте LTV `reject` (> 85) и пробег > 400 000 — что важнее:
   `reject` (вариант A, по умолчанию) или `review` (вариант B, «пробег
   перекрывает всё»)? Формулировка «иначе решение review» допускает оба
   прочтения.
2. Пустой пробег: пустая строка нормализуется в 0 и обходит правило,
   отсутствующий ключ / `null` — ошибка валидации. Это ожидаемое
   поведение, или пустое значение должно быть ошибкой? Нужна единая
   трактовка `''`, `null` и отсутствия ключа.
3. Пробег > 500 000: оставить `ValidationException` (как сейчас) или
   правило «> 400 000 → review» должно охватывать и его — тогда придётся
   менять `max_mileage_km`?
4. Подтвердить границу: 400 000 км включительно не переводит заявку в
   `review` («не больше 400 000» = 400 000 проходит)?
5. Порог пробега одинаков для всех заявок или должен зависеть от
   возраста авто (связка с `ltv_by_age` / задачей LOAN-12)?
6. Нужно ли возвращать причину `review` в ответе API (сейчас `decision` —
   строка без объяснений)? В скоуп не входит, но влияет на будущую спеку.
