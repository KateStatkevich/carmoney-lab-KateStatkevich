# intent_MILEAGE — правило «пробег не больше 400 000 км»

Дата: 2026-10-08. Задача MILEAGE: добавить в расчёт решения по заявке
проверку пробега авто — не больше 400 000 км, иначе решение `review`.

## Намерение

Если пробег авто больше 400 000 км, решение по заявке — `review`, а не то,
что говорит LTV. Граница 400 000 км — включительная: ровно 400 000 км
остаётся в `approve`-зоне (при низком LTV), в `review` уходит только
400 001 км и выше.

Правило меняет вердикт, а не валидацию: заявка с пробегом 400 001+
остаётся валидной (порог валидации `max_mileage_km` = 500 000 не меняется).
Поэтому правило встраивается в `DecisionEngine`, а не в `ApplicationValidator`.

## Зафиксированные решения (Grill Me, 2026-10-08)

1. **Приоритет при конфликте — вариант A.** LTV `reject` (> 85) сильнее
   пробега: проверка `reject`/`review` по LTV не ослабляется. Пробег только
   не даёт `approve` (понижает до `review`), «пробег перекрывает всё» —
   отклонено.
2. **Пустой пробег — ошибка валидации.** Отсутствующий ключ, `null` и
   пустая строка трактуются одинаково как неуказанный пробег →
   `ValidationException`. Значение 0 допустимо только при явной передаче.
   Это меняет текущее поведение: сейчас пустая строка нормализуется в 0
   и проходит валидацию. Расширяет scope: правится `ApplicationValidator`
   (в плане был «не трогаем»).
3. **Граница 400 000 км — включительно.** 400 000 + низкий LTV →
   `approve`; 400 001+ → срабатывает правило.
4. **Матрица решений (подтверждена):**
   - LTV < 60 + пробег ≤ 400 000 → `approve`
   - LTV < 60 + пробег > 400 000 → `review`
   - LTV 60–85 → `review` независимо от пробега
   - LTV > 85 → `reject` независимо от пробега
   - при `review` и `reject` `approved_limit` = 0 (текущее поведение
     `AssessmentService`, не меняется).
5. **Пробег > 500 000 — вне scope.** `max_mileage_km` = 500 000 и текст его
   ошибки не меняются: свыше 500 000 — `ValidationException`, до решения
   заявка не доходит. Правило реально срабатывает только в диапазоне
   400 001–500 000.

## В scope

- `backend/config/rules.php`: новый порог `review_max_mileage_km = 400000`
  в блоке `vehicle` рядом с `max_mileage_km` (порог вердикта, не граница
  валидации).
- `backend/src/Domain/DecisionEngine.php`: конструктор принимает
  `int $reviewMaxMileageKm`; `decide(float $ltv, int $mileage): string`;
  `approve` — только при `LTV < approve_max` И `mileage <= 400 000`;
  док-блок синхронизируется с кодом (сейчас `<=` vs `<`).
- `backend/src/Domain/AssessmentService.php`: `decide($ltv, $input['mileage'])`.
- `backend/src/AppFactory.php`: передача порога из `$rules['vehicle']`
  вторым аргументом конструктора `DecisionEngine`.
- `backend/src/Domain/ApplicationValidator.php` (расширение по решению 2):
  пустые значения (`''`, `null`, отсутствие ключа) → `ValidationException`
  с ошибкой по ключу `mileage`; `0` — валиден только явно переданный.
- Тесты: `DecisionEngineTest` (матрица «399 999 / 400 000 / 400 001 ×
  LTV-зоны», пересечения с границами LTV 59.99 / 60.0 / 85.0 / 85.01),
  `AssessmentServiceTest` (сквозное трио границ, включая reject-зону
  LTV 95 — по решению 1 ожидание `reject`), `ApplicationValidatorTest`
  (характеризация: `''`/`null`/отсутствие ключа → ошибка; 0 валиден;
  границы 500 000 / 500 001). Существующие ассерты не меняются; старые
  вызовы `decide()` получают нейтральный пробег (например, 100 000).

## Вне scope (подтверждено)

- Фронтенд: поле `mileage` уже `required`, вердикт `review` отображается
  как есть.
- Контракт API: состав полей ответа не меняется.
- Причина `review` в ответе API (сейчас `decision` — строка без
  объяснений).
- Порог, зависящий от возраста авто (`ltv_by_age`, задача LOAN-12).
- Изменение `max_mileage_km` и текста его ошибки.
- Миграции БД (`vehicles.mileage_km` не меняется).
- Feature-тесты с БД.
- Обновление `docs/setup/code_map.md` (раздел точек вставки MILEAGE
  устареет) — отдельная задача документации после приёмки.
